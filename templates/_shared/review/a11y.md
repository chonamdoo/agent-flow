# Review Angle: Accessibility

Check that user-visible UI is reachable and operable for keyboard, screen
reader, and high-contrast users. Focus on changes that add or modify UI.

## What to verify

1. **Semantic structure**
   - Interactive elements use the right element (`<button>` vs `<a>` vs
     `<div onClick>`). `<div>` with click handlers requires `role`+`tabindex`.
   - Headings form a logical outline; no level skipped for visual styling.

2. **Labels and names**
   - Every form input has an associated label, `aria-label`, or
     `aria-labelledby`.
   - Buttons with icon-only content carry an accessible name.
   - Images have `alt`; decorative images use `alt=""`.

3. **Keyboard access**
   - All actionable elements reachable by Tab; no positive `tabindex`.
   - Focus visible on `:focus-visible`; modals trap focus and restore on close.
   - Escape closes overlay; Enter/Space activates buttons.

4. **Screen reader announcement**
   - Async results use live regions (`aria-live="polite"` for non-urgent).
   - Route changes update `document.title`.
   - Dynamic errors are announced, not silently rendered.

5. **Contrast and motion**
   - Text/icon contrast meets WCAG AA (4.5:1 small text, 3:1 large/icons).
   - Animations respect `prefers-reduced-motion`.

## Output format

```text
## Accessibility review findings

verdict: approve | request-changes

### Must-fix
- <severity:high> [path:line] <statement>. WCAG ref or principle.

### Should-fix
- <severity:med> ...

### Notes
- <severity:low> ...
```

Cite paths as `path/to/file:line`. Keep total under 150 lines.

Emit exactly one unfenced final verdict line: `verdict: approve` or `verdict: request-changes`.
