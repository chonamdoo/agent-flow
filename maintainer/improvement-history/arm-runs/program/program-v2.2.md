## 두 리뷰의 공통 결론: 나중에, 전제 조건 뒤

- **pstack은 근거를 내지 않는다.** 역할-모델 대응표만 있고, 비용·품질·속도 근거나 효과 측정이 없다.
- **agent-flow는 pstack식 분리를 지금 표현할 수 없다.**
  - explorer·planner·implementer·fixer는 모두 controller 세션 모델로 돈다. `roles/default.yaml`에는 모델 칸이 없다.
  - 모델을 고를 수 있는 곳은 multi-review 리뷰어 subprocess뿐이다.
  - 그래서 지금 가능한 분리는 "판단 역할인 리뷰어를 싸게"인데, 이는 pstack과 반대 방향이다. 구현자를 싸게 하려면 runner를 바꿔야 하고, runner는 금지 구역이다.
- **측정 함정**
  - 모델 계열을 바꾸면 비용만이 아니라 행동도 바뀐다. 그래서 "할당 정책 전체"의 효과로만 해석한다.
  - 리뷰어와 fix-loop가 맞물려 있다. 약한 리뷰어는 라운드와 비용을 줄이지만 결과물을 나쁘게 한다. 강한 리뷰어가 약한 구현자를 받치면 라운드가 늘고 상한 정지가 늘 수 있다.
  - 리뷰어 subprocess 토큰은 지금 재지 않는다(`reviewer_jobs`는 개수뿐). 그래서 C의 비용과 오케스트레이션 비율은 리뷰어 몫만큼 작게 나온다.
  - 평가 컨테이너에서 실제로 쓸 수 있는 모델은 `claude-opus-5-5`만 확인됐다. 싼 모델 쌍은 확인되지 않았다.
- **위치**: Q2 탐색 차원이 아니라 Q2 뒤의 별도 질문이다(리뷰어 모델 하나만 Q2 차원으로 넣는 안은 Claude 리뷰의 선택지로 남긴다). Q4(플로우 선택)와도 별개다.

## 지금 바로 하는 것 (계측만, 조건 추가 없음)

| 항목 | 내용 |
|---|---|
| 리뷰어 계측 | 리뷰어 작업마다 provider, model, effort, 토큰, 비용, 재시도를 run 기록과 `phase_trace`에 남긴다. 측정할 수 없으면 "측정 안 됨"으로 적고, 그 run의 비용 우월 판정을 막는다 |
| 모델 가용성 사전 점검 | 평가 컨테이너에서 실제 호출로, 정확한 모델 id와 effort 지원을 확인한다. 쓸 수 없으면 실패로 닫는다. 몰래 다른 모델로 대체하지 않는다 |
| 리뷰어-fix-loop 기록 | 리뷰어별 지적 수, fix-loop 라운드, 상한 정지, 수리 비용. 첫 산출물과 최종 산출물을 둘 다 남긴다 |
| 사전등록 문구 | "모든 조건이 같은 모델"을 "workflow 비교는 같은 모델, 할당 비교는 별도 질문"으로 고친다 |

## 시작 조건 (모두 충족)

1. A/A 보정과 잡음 바닥이 끝났다.
2. 리뷰어 비용이 측정되고, run 비용에서 의미 있는 몫이다(예: 20% 이상).
3. 더 싼 모델이 평가 컨테이너에서 실제로 쓸 수 있음이 확인됐다.
4. 천장이 아닌 과제가 있다(후속 변경, 아키텍처 규칙이 갈리는 과제).

## 시작하면

- Q2 승자 workflow를 고정하고, 균일 Opus를 할당 L과 비교한다.
- 다른 것은 모두 고정한다: 평가기, snapshot, 리뷰어 수, gate, 상한, 예산, 후속 에이전트.
- 채택 규칙은 Q2와 같다. 모든 주 지표가 비열등이고, 무결성 위반이 0이고, 총비용이 우월해야 한다(리뷰어 포함, 측정 안 된 비용이 있으면 판정 불가).
- 구현자를 싸게 하는 분리는 runner 변경이 필요하다. 그래서 별도 질문(Q5)으로 두고, 사용자 승인 뒤에만 한다.
