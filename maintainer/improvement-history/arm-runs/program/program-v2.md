# #409 실험 프로그램 v2 (승인 요청안)

v1 초안을 다음 세 가지로 고쳤다.
- Claude·Codex 적대적 리뷰. 서로 독립으로 했고 지적은 각각 20여 개다.
- 아키텍처·소프트웨어 공학 품질 측정 조사.
- karpathy/autoresearch PR 검토.

가장 큰 변화: **첫 단계는 workflow 순위를 매기지 않고 측정 장치를 검증한다.** 품질은 대리 지표보다 **결과(후속 변경이 쉬운가)**로 잰다.

## 1. 질문과 주 지표 (사전등록할 것은 이것뿐)

| | 질문 | 주 지표 | guardrail |
|---|---|---|---|
| Q1 | agent-flow가 맨 모델보다 나은가 | ① 기능 성공 S(비공개 검사) ② **후속 변경 성공률**(유지보수성) ③ **비공개 아키텍처 규칙 위반 수** | 무결성 위반 0, 비용 |
| Q2 | 품질을 지키며 줄인 축소판이 있는가 | 위 ①②③ 비열등. 허용 폭은 감당 가능한 n에 맞춰 넓게 잡는다(예: −0.15). 비용은 우월 | 같음 |
| Q3 | 기획이 부족할 때 인터뷰가 도움이 되는가 | **나중 별도 연구**(§7) | |

- **UI 과제(웹·앱)는 주 지표 ④ 디자인 충실도를 더한다**(§3e). 내용은 배치 충실도와 토큰 준수다.
- 나머지 지표(중복, 복잡도, 보안, 심판 점수, 시각 유사도 등)는 **탐색**으로만 보고한다. 결정에 쓰지 않는다.
- 단위는 run이다. 과제로 블록을 나누고, 과제별 결과를 따로 보고한다. 결론은 "이 과제들"에 대한 것이고, 일반화하지 않는다.
- 미완성 run(상한 정지, 빌드 실패)도 분모에 넣는다. 품질이 없는 run은 "산출물 없음"으로 따로 센다. 미완성 run의 diff가 작아 품질이 좋아 보이는 일을 막기 위해서다.

## 3. 평가기 확장 (비공개, 모든 조건에 같게)

### 3a. 무결성 ("됐다고 했는데 안 했다")

- 원래 테스트 스위트를 seed 원본으로 덮어쓴 뒤 다시 돌린다(이미 함).
- 테스트 변조를 탐지한다.
  - 삭제, `@Ignore`, `.skip`, `assumeTrue(false)`
  - 단언 약화(테스트 diff)
- stub을 탐지한다.
  - `TODO()`, `NotImplementedError`, 빈 본문
  - 테스트 fixture 값을 하드코딩한 반환
  - 대상 자체를 mock하는 것
- 최종 메시지의 주장을 원자 단위로 나눈다(구현함, 테스트 돌림, 통과함, 범위). 실제 도구 로그와 산출물로 대조한다. "근거 없음", "모순", "빠뜨린 필수 작업"을 따로 센다.

### 3b. 결정적 구조 지표 (base commit 대비 diff로, 탐색용)

| 축 | 지표 | 도구 |
|---|---|---|
| 아키텍처(주 ③) | **비공개 아키텍처 규칙**(run 전에 과제별로 작성하고 어느 조건에도 보이지 않음)으로 새로 생긴 위반 수, 새 의존 순환, Gradle 모듈 그래프에 생긴 잘못된 방향의 간선 | Konsist / dependency-cruiser + 모듈 그래프 diff. 기존 위반은 동결 |
| 비대 | **기존 함수의 성장**(touched 파일), 복잡도 집중도(SlopCodeBench의 erosion 정의), 임계 초과 함수 수. Composable과 테스트는 따로 | detekt CognitiveComplexity·LongMethod, ESLint |

| 범위 | 사전 작성한 허용 경로 밖 수정, 새 의존성, 포맷 churn. `.agent-flow/`와 문서는 제외 | git diff |

LCOM, Martin D, Maintainability Index, Sonar debt 분은 쓰지 않는다. 조사 결과 타당성이 약하거나 논쟁 중이다.

### 3c. 행동 지표: 후속 변경 (주 ②, 유지보수성의 기준)

- 각 조건의 결과물 위에, **고정된 후속 에이전트**(맨 모델, 같은 모델, kit 없음)가 미리 써 둔 후속 변경 2개를 차례로 한다.
- 후속 변경은 아키텍처 이음매를 지난다. 예: 필드를 Room → repository → 화면까지 끝에서 끝으로 추가, 데이터 소스 교체.
- 잰다: 후속 변경의 숨은 검사 통과율, 비용, 바꾼 파일 수(국소성), 새 회귀.
- 근거: CodeThread(ICML 2026)는 에이전트 코드 위에서 후속 PR 성공률이 1~13%p 떨어졌다. 그 차이를 전통 지표는 설명하지 못했다. SlopCodeBench는 품질 프롬프트가 처음 품질은 올리지만 열화는 막지 못함을 보였다.
- 타당성 확인: 기준 구현과, 일부러 결함을 넣은 기준 구현(god function, 계층 위반, 중복 헬퍼) 위에서 후속 변경 비용이 실제로 갈리는지 먼저 본다.

### 3d. LLM 심판 (보조, 검증을 통과한 항목만)

- 0~3점의 원칙 8개를 버리고, 근거를 붙인 **이진 항목 최대 6개**만 둔다. 예:
  - 기존 패턴과 유틸을 재사용했는가(과제별로 이름을 적음)
  - UI·라우트 계층에 비즈니스 로직이 없는가
  - 기존 오류 처리 규칙을 따르는가
  - 부작용이 격리되어 있는가
  - 새 함수의 추상 수준이 한결같은가
  - "해당 없음"과 "맥락 부족"도 허용한다.
- explicit receivers와 매개변수 최소화는 보편적 미덕이 아니라서 심판 축에서 뺀다. Kotlin 규칙이 필요하면 detekt로 따로 잰다.
- 정제
  - 운영 코드만 준다. 포맷을 통일하고 주석을 지운다. workflow 산출물은 뺀다.
  - **조건 맞히기 시험**에서 정답률이 50%를 넘으면 blind가 깨진 것이다. 그러면 조건 간 주장에 쓰지 않는다.
- 심판은 에이전트와 다른 계열 하나를 쓰고, 점수는 절대 채점이다. pairwise는 검증 표본에만 쓴다. 인용한 줄이 실제로 있는지 기계로 확인한다.
- 보정 세트
  - 결함 mutant
  - **정상 리팩터 mutant**(점수가 바뀌면 안 됨)
  - **과잉 추상화 mutant**(벌해야 함)
  - 길이만 맞춘 쌍(장황함 편향)
- 사람 기준 세트: 30~50개에 사람이 라벨을 붙인다. 심판과 사람의 일치도(가중 κ)를 항목별로 낸다. 낮은 항목은 버린다.
- 심판 결과는 결정적 지표와 합산하지 않는다.

### 3e. UI·디자인 충실도 (사용자 요청, 2026-10-23)

- 지금 평가기의 한계: OYG는 브라우저 행동 검사, 가로 넘침, 가려짐, 페이지 오류만 본다. 모바일은 testTag와 텍스트만 본다. 과제 입력에 디자인이 없어서 "디자인대로 만들었나"의 기준이 없다.
- 과제에 **디자인 층**을 더한다: 화면별 목업, 디자인 토큰(색·글꼴·간격), 화면 상태(빈·로딩·오류·비활성). 앱은 기존 디자인시스템(`core:designsystem`)을 따르는지도 본다.
- 지표

  | 지표 | 방법 | 도구 | 위상 |
  |---|---|---|---|
  | 배치 충실도 | 요소 유무·순서·상대 위치·크기·간격(허용 오차). 픽셀이 아니라 좌표로 본다 | Playwright DOM 좌표, Compose semantics bounds | 주 ④ |
  | 토큰 준수 | 색·글꼴·간격이 토큰에서 오는지, 하드코딩(`Color(0xFF…)`, 임의 dp, CSS hex)인지 | 정적 검사 | 주 ④ |
  | 상태 구현 | 디자인의 빈·로딩·오류·비활성 상태 | 행동 검사 확장 | 주 ① 안에 |
  | 시각 유사도 | 고정 데이터·글꼴, 애니메이션 끔. 영역별 스크린샷 비교(허용 오차) | Playwright, Roborazzi | 탐색 |
  | 반응형 | 여러 화면 크기에서 깨짐·넘침 | 기존 넘침 검사 확장 | 탐색 |
  | 접근성 | 대비, 라벨·contentDescription, 터치 영역 48dp | axe-core, semantics 검사 | 탐색 |
  | 시각 심판 | 목업 대 구현 스크린샷 루브릭 | 비전 모델, 보정 통과 항목만 | 탐색 |

- 검증
  - 기준 구현에 시각 mutant(간격, 색, 요소 빠짐, 순서 바뀜)를 넣어 지표가 잡는지 본다.
  - 해가 없는 변화(1px, 안티앨리어싱)에는 반응하지 않아야 한다.
  - 기준은 기준 구현이 아니라 디자인 명세다. 그래서 다르게 만든 올바른 구현을 벌하지 않는다.
- 비용: 실행 비용은 거의 없다(결정적). 과제마다 디자인 명세를 만드는 작업이 든다. 디자인 층을 붙인 과제는 새 판으로 내고 기준 구현과 검증을 다시 한다.
- **실기기·에뮬레이터 시각 비교: moru-artemis (사용자 제공, 2026-10-23)**
  - 정체: Google Artemis(Apache-2.0)의 독립 포크이고, Google이 관리하지 않는다. `moru_mcp.py`는 Claude나 Codex 같은 호스트가 기기를 직접 조작하는 stdio MCP 어댑터다. 별도 API 키나 모델 호출은 없다.
  - 쓸 도구
    - `screenshot`, `hierarchy`(UI 요소와 bounds)
    - `capture_baseline` / `compare_current`: 같은 기기에서 기준 화면을 메모리에 잡아 두고, 현재 화면과 픽셀 차이와 요소 구조 차이를 낸다. 임계 16
    - `tap_element`, `scroll_to_element`, `wait_for_element`: 정해진 화면까지 이동
    - `perf_frame_stats`: 프레임 시간
  - 평가기에서 쓰는 방식(LLM이 조작하지 않는 결정적 스크립트)
    1. 같은 에뮬레이터(고정 기기 프로필, 글꼴, 애니메이션 끔, 고정 데이터)에 기준 구현 APK를 설치한다.
    2. 정해진 화면(결제, 주문 내역, 빈·오류 상태)으로 스크립트로 이동해 `capture_baseline`을 한다.
    3. 조건별 산출물 APK로 바꿔 같은 경로로 이동해 `compare_current`를 한다. 픽셀 차이, 구조 차이, 스크린샷, 프레임 통계를 기록한다.
    4. 디자인 목업이 있으면 목업 대 스크린샷도 같은 방식(영역별, 허용 오차)으로 비교한다.
  - Robolectric(Roborazzi) 스크린샷과의 관계: 실기기 렌더링(글꼴, inset, 실제 Compose 그리기)을 보는 보완 수단이다. Robolectric 쪽은 CI에서 싸고 재현이 쉽고, 에뮬레이터 쪽은 실제와 가깝다.
  - **제약**: 이 클라우드 컨테이너에는 `/dev/kvm`(하드웨어 가속)이 없고, 에뮬레이터·시스템 이미지도 없다. 가속 없는 x86_64 에뮬레이터는 띄울 수 없거나 매우 느리다〔추정, 시험 안 함〕. 실행 위치로 다음을 검토한다.
    - (a) 사용자 PC의 에뮬레이터나 실기기(로컬 세션 또는 Remote Control)
    - (b) KVM이 있는 다른 실행 환경
  - 보안: 업스트림 `start.sh`는 전역 MCP 설정과 IDE 규칙을 설치한다. 그래서 쓰지 않는다. `uv sync`와 `moru_mcp.py` 등록만 한다. 받은 zip은 실행하지 않고 내용만 검토했다.

## 4. 장치 검증 (첫 단계, 순위 매기기 없음)

1. **A/A 보정**: 같은 설정을 두 변형처럼 3회씩 돌리고 채택 규칙까지 통과시킨다. 승자가 나오면 규칙이 잡음에 끌리는 것이다.
2. **지표별 잡음 바닥**: 반복 run으로 조건 안 분산(ICC)을 잰다. Δ < 2σ인 차이는 차이로 보지 않는다.
3. 아키텍처 규칙, 후속 변경, 심판을 seed·기준 구현·결함 주입본에 돌려 각각 제대로 반응하는지 확인한다.
