v2(`program-v2.md`)를 사용자가 승인했다. 그 뒤 두 가지가 들어왔다. 바뀐 것만 여기 적고, 나머지는 v2 그대로다.

1. 사용자 요청: UI는 더 복잡한 탭 구조로, 무신사 모바일 과제에서
2. 사용자 질문: pstack처럼 에이전트가 필요한 플로우를 스스로 고르는 실험도 필요한가. 적대적 리뷰 두 개를 받았다.
   - `reviews/BRIEF-router.md`: 요청문
   - `reviews/claude-adversarial-router.md`, `reviews/codex-adversarial-router.md`: 리뷰 결과
   - `research/pstack-summary.md`: pstack 요약

## 1. 사용자가 정한 기본값

## 2. 새 과제: mobile-tabs (비공개, holdout 후보)

- seed: sduiTest + mobile-cart v0·v1 + mobile-checkout 기준 구현. sduiTest는 무신사 과제·면접 준비 저장소이고, 실물 스펙(하단 탭 5개, 카테고리 탭 줄, 카테고리 시트)이 이미 있다.
- 요구: 셸을 슬롯 구조로 바꾼다. 그 위에 다음을 만든다.
  - 탭마다의 화면 쌓임

  - 페이지마다 스크롤을 유지하는 홈 카테고리 페이저
  - 마지막 카테고리 기억(DB v7)
  - 좋아요 배지, 2열 카테고리 시트, 배치 규칙
- 비공개 검사는 29개다.
  - 행동: 탭, 뒤로 가기, 스와이프, 스크롤 유지
  - UI 배치: 같은 너비, 배지 위치, 표시줄 위치, 2열 격자를 semantics 좌표로 본다
  - 데이터: Room, 마이그레이션
- 기능 S 외에 아키텍처(슬롯 셸, DI 경계), 후속 변경, UI 배치를 비교하는 데 쓴다.

## 3. "에이전트가 플로우를 고른다" (Q4로 따로, 지금은 하지 않음)

두 리뷰의 결론이 같다: **나중에, 전제 조건이 채워지면.** 지금 과제는 모두 기능 추가라 고를 것이 없다. n=3과 $150 사이클로는 잡음만 더한다.

- 형태를 나눈다.
  - **R1**: 시작할 때 workflow 하나를 고른다.
  - **R2**: 한 workflow 안에서 phase 깊이를 고른다. `default`가 이미 이렇게 한다고 적혀 있다.
  - **R3**: 중간에 바꾼다.
  - 이 셋을 한 "적응형" 조건으로 섞지 않는다.
- Q4는 Q2의 탐색 차원이 아니라 별도 질문이다. Q2는 고정 workflow를 찾고, Q4는 고르는 정책을 평가한다.
- Q4를 시작하는 조건(모두 충족)
  1. A/A 보정과 잡음 바닥이 끝났다.
  2. 섞인 과제 묶음(버그 수정, 리팩터, 기능, UI)에 전체 비공개 평가기가 있다.
  3. 그 묶음에서 고정 조건들로 잰 **oracle 격차**(과제마다 가장 좋은 고정 플로우와 가장 좋은 단일 고정 플로우의 차이)가 잡음 바닥보다 크다.
  - 격차가 없으면 어떤 router도 가장 좋은 고정 기본값을 이길 수 없다. 그 플로우를 출시하고 Q4는 접는다.
- 시작하면 이렇게 한다.
  - R1부터 한다. 메뉴는 `bugfix`, `development`, Q2 승자 S*다(S*가 development와 같으면 뺀다).
  - 메뉴의 각 플로우를 고정 조건으로도 같은 과제에서 돌린다. 그래야 잘못 고른 것과 잘 골랐는데 실행이 나쁜 것을 가를 수 있다.
  - 비교 대상은 개발 과제에서 고른 최선 고정 플로우다.
  - 기록: 고른 플로우와 실행 전 이유, 고르는 데 든 비용, 실제로 돈 phase, fallback.
  - 채택: 모든 주 지표가 비열등이고, 무결성이 지켜지고, 총비용이 줄어야 한다. 아니면 고정 기본값을 유지한다.

## 4. 지금 바로 바꾸는 것 (두 리뷰가 v2에서 빠졌다고 지적한 것)

| 바뀜 | 내용 |
|---|---|
| **조건 D 추가** | `default` workflow(R2를 주장함). 출시 기본값 후보인데 v2는 한 번도 재지 않았다. B·C와 같은 방식으로 돌린다. phase를 실제로 접는지는 기록으로 확인한다 |
| **phase 기록** | 모든 run에 실제로 돈 phase, 건너뛴 phase, 각 phase의 토큰·시간을 남긴다(harness가 runner 상태와 transcript에서 뽑는다. runner 변경 없음) |
| **비용 분리** | 오케스트레이션 비용(승인, 리뷰, gate)과 작업 비용을 따로 보고한다 |
| **§5 채택 규칙 고침** | 주 지표 ① 하나가 아니라 **①②③(UI 과제는 ④까지) 모두 비열등**이어야 채택한다. 잡음 바닥은 "차이로 보지 않는 폭"일 뿐 비열등 증명이 아니므로, 반복과 불확실성 구간을 함께 보고하고 "결론 없음"을 허용한다 |
| **출시 규칙** | Q1·Q2 결과를 기본값 선택으로 바꾸는 규칙을 미리 적는다. 모든 주 지표가 비열등인 후보 가운데 총비용이 가장 낮은 것. 그런 후보가 없으면 현행 유지 |
| **과제 유형 표시와 섞인 묶음** | 과제마다 유형(기능, 버그 수정, 리팩터, UI)을 적는다. 결과는 유형별로도 낸다. 버그 수정·리팩터 과제는 Q4 전제 조건이라 나중에 만든다 |
| **oracle 격차 계산** | 고정 조건 결과만으로 과제별 최선과 단일 최선의 차이를 계산해 보고한다. 추가 run은 없다 |
