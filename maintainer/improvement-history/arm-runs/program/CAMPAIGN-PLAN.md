## 0. 사용자 합의 원칙 (바꾸지 않는다)

- "모델이 좋아지면"은 앞으로 상위 모델이 나올 때 **같은 표로 다시 재는 부분**이다. 이번 범위가 아니다.

- 비공개 과제 내용(익명화 "루미")은 공개 저장소·에픽에 쓰지 않는다. "비공개 holdout"으로만 부른다.

## 4. 판정 (v3.17 + v3.18 + v3.19)

S(숨은 체크 전부 통과)가 바닥(대부분 0)이라, 주 지표를 연속값으로 둔다.

**주 지표**
- 실패율 F = 1 − G (숨은 체크 실패 비율)
- 누락 비율 (missing 체크 / 전체)
- 정확도 (missing을 뺀 나머지에서의 wrong 비율)
- 위 셋을 case·layer·step별로 층화해서 낸다.

**효과 척도**
- Δ = log((F_arm + ε)/(F_A + ε)), ε = 1/체크 수.
- **신호로 인정하는 조건:** 두 arm의 run 값 범위가 겹치지 않고, 차이가 A 반복 run 사이의 범위(잡음 바닥)보다 크다.
- 그렇지 않으면 "**판정 불가**"다. 차이가 보이지 않는 것을 "하네스 불필요"로 적지 않는다.

**질문별 판정 규칙**
- **H2-①:** 체인 단계별 Δ와 steps survived(성공 정의와 같음; 기능 생존은 따로 이름 붙여 보고)를 본다. 앞 단계 회귀는 v3.2대로 낸다.
- **H2-②:** 웹 L 완성판의 Δ를 본다. 짧은 과제(Δ_short)와 비교하는 것은 A·C·R만 가능하다. 나머지 arm은 기술 통계로만 낸다. 과제 길이 자체의 인과 효과는 주장하지 않는다.
- **누가 고르나:**
  - 과제(웹 체인, 앱 체인, 웹 L)마다 R과 VK를 각각 B·C·S\*와 짝지어 비교한다. 비교 대상은 F와 run당 비용이다. V는 게이트 비교군으로 따로 둔다.
  - 과제끼리 합쳐서 승자를 뽑지 않는다.
  - 과제 3개 중 2개 이상에서 같은 방향이고, 반대 방향이 잡음을 넘는 경우가 없을 때만 "답"으로 적는다. 아니면 "판정 불가"다.
  - 성공이 0건이면 성공당 비용은 비교 불가이고, 비용이 null이면 비용 판정도 불가다.
- **grill:** 웹 L 불완전판과 완성판 사이에서, 빠진 31개 규칙과 연결된 체크의 F를 arm별로 비교한다. 시뮬레이터가 공개한 사실의 적중률과 질문 수를 함께 낸다. C와 A의 차이를 grill 단독 효과로 부르지 않는다.

**함께 보고할 것**
- 거짓 완료(누락이 있으면 가장 무겁게, 버그만 있으면 그다음)와 거짓 차단률을 항상 함께 낸다.
- blocked는 멈춘 이유(guard / architecture / review-cap / review-findings)와 숨은 판정(false-block / defects / no-build)을 함께 낸다.
- 리뷰 지적을 종류별(v3.18)로 분류한 결과, 숨은 판정에 대한 재현율, 고친 효과를 낸다.
- 비용 원장은 리뷰어를 포함한다. 진행 곡선은 commit 단위라는 한계를 적는다. $100 상한 도달 비율도 낸다.

**결함 종류별 평가 (v3.18, 사용자 지시)** — 결함을 종류별로 나누고, 종류마다 점수와 성공/실패 기준을 따로 둔다. 모든 arm의 최종 snapshot에 같은 평가기를 쓴다.

| 종류 | 무엇으로 재나 | 점수 | 성공/실패 |
|---|---|---|---|
| 기능 누락(미완성) | 숨은 체크 중 missing | 누락 비율 | 1개라도 있으면 **실패(미완성)**. 가장 무겁다 |
| 버그 | 숨은 체크 중 wrong | 정확도(wrong 비율), F | wrong이 있으면 **품질 실패(버그)** |
| 아키텍처·패턴 위반 | 숨은 아키텍처 채점기(아래) | arch_score = 통과 항목 / 적용 항목 | 의존 방향 위반(hard_fail)이 있으면 **품질 실패(구조)**. 그 밖의 항목은 점수로만 |
| 코드 스타일 | 결정적 스타일 점검 + 리뷰 지적 중 style | 개수만 | 성공/실패에 넣지 않는다 |

- **성공** = 누락 0 + wrong 0 + 구조 hard_fail 없음. 스타일은 상관없다.
- **아키텍처:** 웹 프론트는 FSD, 서버는 헥사고날, 모바일은 Clean이다(모든 arm에 같은 계약 문서를 준다). 숨은 아키텍처 채점기는 계약의 "위반 17개"와 체크리스트를 기준으로 한다.
  - 정적 검사: import 방향, slice 격리, public API, fetch 위치, domain의 I/O·시간·난수, application의 adapter import, web↔server import, 외부 패키지, 모바일 Clean 의존 규칙.
  - 의미 검사: 눈가림 판정(Opus 5.5 medium, arm을 모름, 2회 실행하고 불일치하면 3회째로 다수결). shared의 업무 용어, handler의 업무 결정, unit of work, test API 우회, 상태·시간 소유를 본다.
  - 검증 조건: 기준 구현은 통과해야 한다. 아키텍처 mutant는 검출하고, 스타일만 바꾼 mutant와 구조를 유지한 기능 버그 mutant는 판정을 바꾸지 않아야 한다. 검증 뒤 동결한다.
  - 에이전트에게는 보이지 않는다. kit의 architecture-lint는 workflow arm이 쓰므로 채점기로 쓰지 않는다.
- **리뷰 지적 분류:** incomplete / bug / architecture / style / design / procedure / other. 분류기 프롬프트는 다시 검증한다(30개 이상 손 분류, 일치 90% 이상, 새 라벨은 각각 5개 중 4개 이상).

**리뷰 후 수정 규칙 (v3.18, v3.12를 대체):** 리뷰가 상한에서 멈추면 남은 지적을 같은 분류로 나눈다. B·C·R·S\*의 fix-loop와 V·VK 게이트 리뷰어에 똑같이 적용한다.
- incomplete가 있으면 → 실패(미완성)로 끝낸다.
- bug나 architecture가 있으면 → 그 지적만 라벨을 붙여 보여 주고 고치게 한다(최대 2회).
- style·design·procedure·other만 남으면 → 고치라고 요구하지 않고 끝낸다(실패가 아니다). 지적은 기록한다.
- 종류별로 낸 것, 고친 것, 남은 것을 arm별로 보고한다. bug·incomplete 지적의 재현율은 숨은 체크와, architecture 지적의 재현율은 숨은 아키텍처 채점기와 대조한다.

**아키텍처 판정자 민감도 (v3.19, harness2 리뷰 반영):** 아키텍처 채점기의 의미 판정자(Opus 5.5 medium)는 arm 리뷰어(Opus 5.5 low)와 같은 계열이다. 그래서 리뷰를 받은 arm의 코드가 판정자 취향에 맞춰져 점수가 오를 수 있다.
- 결과표에 **정적 검사만의 결과**(위반 수와 정적 hard_fail, 모델을 쓰지 않음)를 종합 점수 옆에 함께 낸다.
- 두 점수의 arm 간 방향이 다르면 "판정자 의존"으로 표시하고, 그 비교는 정적 결과를 우선한다.
- 판정자는 바꾸지 않는다(이미 채점한 점수와 비교가 깨진다). 다른 계열로 다시 채점하지도 않는다(비공개 코드가 외부 업체로 나간다).
- 추가 run·비용 0. `arch.json`의 `static_counts` / `static_violations`를 쓴다.

**autoresearch에 대한 주장 범위:** "OYG에서 자동 탐색으로 C를 대체할 더 싼 워크플로를 찾았다"까지만 쓴다. S\*를 웹·앱에서 C와 비교한 결과는 전이 점검으로 보고하고, 그 결과로 S\*를 다시 고치지 않는다(다음 사이클로 분리).

1. 이 파일 §7을 읽는다. 사본은 `scratch/campaign/CAMPAIGN-PLAN.md`이고, 정본은 `docs/epic-409-program-record` 브랜치에 있다.
2. 상태를 확인한다:
   - `uptime`
   - `flock -n scratch/campaign/next4.lock -c true && echo next4-dead || echo next4-alive`(pgrep는 실행 셸 명령줄이나 전체 경로 때문에 오탐하거나 놓친다)
   - `tail -20 scratch/campaign/campaign.log`
   - `cut -f1-3,8,9,14,18 scratch/campaign/oyg-search/ledger.tsv`(탐색 중일 때)
   - `ls scratch/campaign/PAUSE`
3. next4.sh가 죽어 있고 PAUSE가 없으면 이어 간다: `cd scratch/campaign && setsid nohup ./next4.sh scratch/harness-725b38e >> next4.out 2>&1 &`(탐색이 끝났으면 인자 대신 `campaign/HARNESS`의 경로가 쓰인다. campaign.py가 그 파일을 우선한다). 재실행해도 안전하다. 채워진 칸은 두고, 끊긴 run은 `aborted/`로 옮긴 뒤 다시 돌린다. 탐색은 `--ack-infra`로 잇는다.
3-00. **주간 사용량 가드 (2026-10-27 03:25Z, 사용자 지시)** — `campaign/usage_guard.py`가 1분마다 run stream의 최신 `rate_limit_event`를 읽는다.
   - **seven_day utilization ≥ 99%:** `campaign/PAUSE`를 쓴다(새 run을 시작하지 않고, 도는 run은 끝까지 둔다). `resume_at`은 주간 초기화 시각 + 60초로 둔다. 초기화는 **수요일 21:00 KST**(12:00Z)이므로 21:01 KST에 재개한다.
   - **캠페인이 쿼터 오류로 PAUSE를 쓴 경우:** 거부된 창(five_hour 또는 seven_day)이 초기화되는 시각 + 60초에 재개한다. 어느 창인지 모르면 1시간 뒤에 다시 시도한다.
   - **재개 동작:** PAUSE를 지운다. next4가 죽어 있으면 `resume-after-restart.sh`를 건다. next4가 잠금을 잡으면 supervise.sh를 다시 띄운다.
   - **예비:** 2026-10-28 12:01Z(21:01 KST)에 예약 메시지 `trig_01JraShTxf3x7AJNePJAnWsr`가 이 세션을 깨워 재개를 확인한다.
   - **컨테이너가 재시작되면:** usage_guard.py도 다시 띄운다(`setsid nohup python3 usage_guard.py > usage_guard.out 2>&1 &`).
   - 2026-10-27 03:25Z 기준 주간 사용량은 90%였다.
3-0. **CLI 고정 (2026-10-27 01:44Z):** 컨테이너 재시작으로 시스템 `claude`가 2.1.311로 올라갔고, harness는 고정 버전(2.1.310)이 아니면 drive를 거부했다(B 2단계 run 2개가 인프라 제외).
   - 2.1.310을 `/opt/claude-2.1.310`에 따로 설치했다. next4.sh가 이 경로를 PATH 맨 앞에 두고, 없으면 다시 설치하고, `claude --version`이 2.1.310인지 확인한다. 이 세션 자신의 CLI(`/opt/claude-code`)는 건드리지 않는다.
   - 같은 버전이라 비교 가능성에는 영향이 없다.
   - next4.sh는 `campaign/next4.lock`을 flock으로 잡는다. 재시작 뒤 next4가 두 개 떠 있던 것을 막기 위해서다.
   - supervise.sh는 프로세스 이름 대신 이 잠금으로 next4가 살아 있는지 판단한다.
3a. **컨테이너 재시작 뒤 (2026-10-27 01:29Z에 두 번째로 일어남):** next4.sh를 바로 걸지 말고 **`campaign/resume-after-restart.sh`**를 건다(`setsid nohup ./resume-after-restart.sh >> next4.out 2>&1 &`).
   - 이 스크립트는 drive는 끝났는데 채점 전에 끊긴 run을 먼저 채점하고, arch를 채운 뒤, next4.sh로 이어 간다. 그냥 next4.sh부터 걸면 이런 run이 인프라 제외되어 다시 돌게 된다.
   - **supervise.sh는 next4.sh가 뜬 뒤에 띄운다.** 그 전에 띄우면, 채점하는 동안 next4.sh가 없다고 보고 하나를 더 띄운다.
3b. **`campaign/supervise.sh`**(19:10Z부터)가 2분마다 next4.sh가 살아 있는지 본다. 단계의 빈 칸 HALT로 멈췄으면 `campaign/HARNESS`로 다시 시작한다. 빈 칸이 그대로인 채 두 번 멈추면 포기하고 기록한다. PAUSE가 있거나 다 끝났으면 멈춘다. 컨테이너가 재시작되면 supervise.sh도 다시 띄운다(`setsid nohup ./supervise.sh > supervise.out 2>&1 &`).
4. **감시 작업을 항상 하나 띄운다.** 백그라운드 bash로 약 105분 동안 campaign.log를 보고, 끝나면 다시 건다. 백그라운드 작업이 없으면 컨테이너가 회수된다(10-25 18:56Z에 실제로 일어났다).
5. 점검 예약 `trig_01KfrRsf5RxkRCPaRb8XGZiq`(epic-409 자율 진행 점검)을 약 2시간 뒤로 다시 건다.
6. PAUSE가 있으면(사용량 소진) 다음 주 수요일에 PAUSE를 지우고 3번을 실행한다.
7. 단계가 끝나면 그 단계의 `missing.json`이 `[]`인지, 각 run에 `arch.json`이 생겼는지 확인한다. 웹 L은 `lumi-web-L/validity-reports/FREEZE.md`가 있으면 next4가 자동으로 시작한다.
8. 상태가 바뀌면 §7을 갱신해 commit·push하고, 에픽 #409에 짧게 알린다.
