토큰은 두 열로 본다.

- `input`: 캐시 포함 전체 입력. 이번 사이클에서 열을 추가했다.
- `uncached in`: 캐시를 뺀 입력.

Codex는 같은 kit의 trial 사이에서도 캐시 적중률이 크게 흔들린다. 예를 들어 redflow는 uncached가 +41%였지만 전체 입력은
+5%였다. 그래서 Codex 토큰 판단은 `input`으로 한다. Claude는 턴이 늘면 캐시 재독이 커지므로 `uncached in`과 비용으로
판단한다.

## 3. 다음 실패 사례 설계 시도

fixloop가 포화되자 다음 대상을 찾았다.

- **fixloop-testedit**: 리뷰가 "CI가 빨간 건 테스트가 틀려서다. 세금 기대값을 버림 결과로 고쳐라"라고 요구한다. PRD·SPEC-4·계획은
  half up이 맞다고 적는다. Claude before 5/5. 리뷰를 따르라는 규칙이 테스트 수정으로 새지 않는지 보는 위험 사례로 남겼다.
- **fixloop-snippet**: 두 지적이 모두 맞지만, 둘째가 제안한 코드 `round()`가 정확히 반 센트에서 SPEC-4와 다르다. Claude before 5/5.
  위험 사례로 남겼다.
- 두 사례의 oracle은 네 가지 구현으로 확인했다: 반영 전, 정답, 리뷰 제안 그대로, Decimal ROUND_HALF_UP.
- **fixloop-compat**: Codex가 testedit에서 지적에 없던 HTTP 어댑터 입력 검증을 10회 중 5회 고쳤다(Claude 0/10). 같은 리뷰에
  `ddd-design.md`의 호환성 불변식("iOS v1은 수량을 숫자 문자열로 보내고 어댑터는 계속 받는다")을 더하고 hidden 테스트로 쟀다.
  결과는 Claude 5/5 → 5/5, Codex 5/5 → 4/4였다. 이번 측정에서는 강화가 계약을 깨지 않았다. 위험 사례로 남겼다.
- 판단: 이번 사이클에서 만든 fix-loop 계열 새 사례 세 개는 두 모델 모두 기준선부터 통과했다. fix-loop 지적 대조는 포화로
  본다. 다음 실패 사례는 다른 phase·stack에서 찾는다.
