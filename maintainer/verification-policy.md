# Agent Flow 개발 검증 기준

이 문서는 Agent Flow 자체를 개발하는 사람과 에이전트를 위한 지침이다. 개발을 시작할 때 읽고 변경 영향에 맞는 검증 범위를 선택한다. 매번 전체 설치와 새 native 앱 작성을 반복하지 않는다.

## 변경 유형별 검증 범위

| 변경 | 필요한 검증 |
| --- | --- |
| 기존 스킬 본문 수정 | 참조와 frontmatter를 확인한다. 행동 지침이 크게 바뀌면 해당 상황만 실제 모델로 평가한다. |
| 스킬 추가·동봉 파일 변경 | 실제 배포 패키지를 대표 fixture에 설치해 선택 여부, 파일 내용, 상대 참조를 확인한다. |
| profile 선택·`requires` 변경 | 영향을 받는 profile의 포함·제외와 전이 의존성을 검증한다. |
| installer·소유권·migration 변경 | fresh install, 재설치, 사용자 수정 보존, 실패 복구 등 관련 설치 회귀를 검증한다. |
| 패키징·host 배포 구조 변경 | 두 installer 진입점과 Claude/Codex/OMP 배포 경로를 검증한다. |

여러 유형이 겹치면 필요한 검증을 함께 적용한다. PR에서는 변경 영향 범위를 검증하고, 배포 전에는 전체 설치 호환성을 확인한다. 영향 범위를 판단할 수 없는 installer 공통 코드 변경은 전체 설치 검증으로 넓힌다.

## 검증의 세 층

### 1. 정적 계약 검사 — 매 PR

누락된 의존 스킬, 깨진 상대 참조, 패키지에 빠진 동봉 파일을 확인한다. 문구 자체를 고정하는 테스트보다 설치 후 사용할 수 있는지를 검사한다.

### 2. 작은 실제 설치 fixture — 설치 관련 변경

Clean/local/pending 사례를 재사용 가능한 작은 회귀 fixture로 유지한다. source 폴더끼리 비교하는 데 그치지 않고 배포할 패키지를 설치한 결과를 확인한다. 설치에 영향을 주지 않는 본문 수정은 전체 설치 행렬을 다시 실행할 이유가 아니다.

### 3. 실제 모델·앱 행동 평가 — 의미가 바뀔 때

파일이 설치됐다는 사실과 모델이 규칙을 올바르게 적용한다는 사실을 구분한다. 스킬이 새로운 판단 기준을 도입하면 정상 사례와 결함 사례를 골라 평가한다. 매번 앱을 새로 만들지 않고 기존 기준 사례를 재사용한다.

### phase skill 전달 회귀 평가

phase가 필요한 skill을 정확히 받는지, 그러면서 쓰지 않는 텍스트에 토큰을 쓰지 않는지를 두 도구로 확인한다. 실행법과 해석 주의점은 `evals/README.md`의 "phase skill 전달 평가"를 따른다.

- `evals/phase_budget.py` — 모델을 쓰지 않는 결정적 측정이다. prompt, skill 본문·frontmatter, workflow YAML, resolver·routing 코드를 바꾸는 PR마다 변경 전 kit과 변경 후 kit으로 돌려 차이를 PR에 기록한다. 다음이 나오면 PR에 원인을 적는다.
  - 변경 전에 필수였던 skill이 어떤 profile·mode·변경 조건에서 빠졌다.
  - Clean이 아닌 mode의 envelope에 Clean `roles`가 들어갔다.
  - phase envelope, 조율 세션, 리뷰어 subprocess의 합계 바이트가 늘었다.
- `evals/phase_eval.py` — 실제 모델 평가다. 기존 정책대로 수동·비차단이다. 판단 기준이 바뀌는 변경을 할 때와 릴리스 전에 돌린다. 기록 항목은 정확도(author의 behavior/plan/norm, 리뷰의 판정 정확도·결함 탐지·오탐), 필수 skill의 실제 읽음률, 토큰, 무효 시행 수다.
- 결과는 `evals/results/phase-<kit 버전>-<YYYYMMDD>/`에 남겨 다음 변경이 이전 결과와 비교되게 한다.
- 평가에서 새로 나온 실패 사례는 `evals/phase-cases/`에 기준 사례로 추가한다.
- `phase_budget.py`는 PR CI에서 돈다. `.github/workflows/tests.yml`의 `phase-budget` job이 테스트 스위트와 병렬로 PR의 base kit과 head kit을 측정하고, `phase-budget-compare` job이 `evals/phase_budget_compare.py`로 위 세 조건을 모든 변경 조건에서 판정한다. 의도한 변화면 PR 본문에 이유를 적고 `phase-budget-accepted` 라벨을 붙인 뒤 비교 job을 다시 돌린다. 보고는 그대로 남고 실패만 면한다.

## 실행과 기록

- 검증 계획에 변경 유형, 영향 범위, 필요한 검증 층과 선택 이유를 기록한다.
- 실행 명령과 실행 위치는 활성 profile의 `gates` 및 기존 검증 정책을 따른다. CI-only 검증을 로컬에서 임의로 실행하지 않는다.
- CI에 넣을 범위와 실제 모델 평가의 실행 조건을 구분한다. 실제 모델 평가는 기존 정책대로 수동·비차단으로 유지한다.
- 큰 검증 기록은 매번 되풀이할 절차가 아니라 작은 회귀 fixture와 기준 사례로 전환할 자산으로 다룬다. 아직 자동화하지 않은 검증을 자동화된 것으로 보고하지 않는다.
- 결과에는 실행한 범위와 관찰한 결과, 실행하지 않은 범위와 이유를 구분해 남긴다.

## 개발 전용 보관 경계

이 문서의 정본은 `maintainer/verification-policy.md`다. 루트 `AGENTS.md`의 installer 관리 블록 밖에서만 참조한다. 설치용 `bootstrap` 템플릿이나 공용 `skills`에 복제하지 않는다.

`maintainer/`를 배포 파일 목록이나 installer 복사 대상에 추가하지 않는다. `docs/`는 현재 npm 배포 대상이므로 이 지침을 그곳으로 옮기지 않는다. 패키징 또는 설치 경계를 변경할 때 문서와 개발 전용 참조가 배포·설치 결과에 포함되지 않는지도 확인한다.
