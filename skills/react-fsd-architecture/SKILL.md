# React Web Feature-Sliced Architecture

Apply this skill when an existing React Web/Next.js application's architecture mode is **stack** (this skill is then the selected architecture contract) or when its **local architecture contract adopts FSD** (this skill is then an adjunct, and the local contract governs where they differ), or when explicitly evaluating FSD as a candidate. Selection does not come from a `.tsx` extension, a `features/` directory, or this skill alone. Identify the affected app/package and its selected architecture first. An admin app organized by route sections may validly retain route-scoped `_lib`/`_ui`/`_components` and private-folder boundaries; do not impose the front-office FSD layout on it. Clean Architecture has a separate contract. No architecture switch, folder migration, dependency install, or form-library migration is implicit.

## Make the placement decision

1. Inspect the actual route tree, owners, callers, import rules, and existing slice/export conventions. Preserve framework URL contracts and existing working boundaries; FSD's canonical Next.js example with a separate `_app`/`_pages` tree is an option, not a reason to move a live router. Name what behavior is route-only, what must be reused, and which state/effects it owns.
2. Keep route files responsible for routing, metadata, providers, server composition, and route-only UI/state that needs no independent cross-route owner. A large one-off screen block can remain route-local. Put reusable or independently composed large UI regions in `widgets`; place a meaningful user interaction or business policy in its owning `features` slice, including route-specific policy that needs its own boundary. Put domain-free primitives, focused utilities, transport foundations, and UI receiving data via props in `shared`. If an endpoint-specific fetcher belongs in `shared/api` by the app's established convention, keep that policy; FSD also permits a feature's own `api` segment. Do not put domain workflows or fetching inside a supposedly presentational shared UI primitive.
3. Add `entities` only when a genuinely shared domain concept, mapper, or invariant earns an independent lower-layer owner across consumers. A type used by one feature stays in that feature. A second consumer invites assessment, not automatic extraction. Entity-to-entity composition may justify the FSD `@x` public cross-reference; it is not a general escape hatch for feature-to-feature imports.
4. Follow the selected app's actual segment vocabulary (`ui`, `model`, `api`, `lib`, `config` when useful); keep small slices flat if navigable. Avoid speculative empty layers or pass-through domain/data/presentation tiers. If multiple apps or packages coexist, decide ownership per app; a reusable package needs a real cross-app consumer and its own contract, not borrowed FSD labels.

Placement is complete when every changed responsibility has one owner and consumers can reach it without depending upward or bypassing a sibling's internals. Record unclear ownership as a decision, not a fabricated repo fact.

## Direction, isolation, and public surfaces

- The FSD direction is `app → widgets → features → entities → shared`, omitting unused layers; imports may remain within their own slice or go **down**. `app` and `shared` are special unsliced layers with segments. If the governing contract (this skill in stack mode, or the local contract) treats the Next route folder as app plus page composition, preserve it rather than demanding a separate canonical `pages` layer. No lower-layer import of a higher layer and no sideways feature/widget slice import, whether by alias or relative detour. Resolve a genuinely shared behavior by moving its neutral portion down or combining slices whose ownership is actually one unit; leave unrelated legacy debt out of scope.
- A slice public surface exposes only what consumers need, shielding its internal structure. Inspect the existing repository practice: explicit slice `index.ts` may be appropriate for a new slice where that convention is established or adopted; established deep imports through deliberately stable module paths are a valid alternative. Do **not** create a barrel solely because another project or canonical example has one, nor migrate unrelated callsites. Imports inside a slice remain direct/relative rather than looping through its public entrypoint; imports across slices use the app's configured alias/export convention and obey layer direction.
- In Next.js, trace imports reachable from Client Components. A mixed barrel must not export server-only code into the client graph. If a barrel is used and both environments require entrypoints, expose a separate server-only public surface such as `index.server.ts` and use supported server-only enforcement where the project provides it. Without barrels, separate server and client module paths explicitly. Place `'use client'` at the actual client boundary and keep server secrets/transport/cookies out of that graph. A server component may compose a client feature without making its server data source client-safe.
- TanStack Query, when actually used, owns server snapshots, not arbitrary feature architecture; for keys, hydration, mutations, and cache lifetime read `react-tanstack-query`. For form work, inspect the project's installed library and the touched form: an existing RHF form uses `react-hook-form-zod`, while a selected TanStack Form uses `react-tanstack-form` and owns its draft. Read `react-zod-validation` when a React Web Zod schema, parsing boundary, or inferred input/output changes. Neither form library is forced alongside the other, and prospective TanStack Form usage does not authorize migrating an RHF form or imply Form is installed. Keep these libraries' internal procedures in their own skills.
- In a React Web project actually using Tailwind CSS v4, read `react-tailwind-v4` when changing `className`, `@theme`, responsive/state variants, or shared UI styling. It covers token and class mechanics; FSD still decides which route, feature, widget, or shared UI owns the component. Follow the project's existing styling setup, not a blanket CSS conversion.

## Completion and review decisions

Trace each changed module from its route/consumer through its imports, public surface, and runtime environment. For code changes, exercise the affected route or component through the project's authorized runtime and checks; a passing import rule or a diagram alone does not prove the rendered server/client path. For review, give concrete offending imports and consumer harm; distinguish a documented pre-existing exception from a newly introduced one. Record the architecture mode, governing contract, and observed layout rather than applying this skill's examples as mandatory paths.

- **Success:** A route composes one route-local panel and a reusable interaction from a feature, with shared presentational UI receiving props; imports go down, and a client consumer cannot reach the server fetcher.
- **Valid alternative:** A route-scoped admin section keeps its private `_lib` and `_ui` ownership; or an FSD app with established deep imports exposes a narrow stable module path instead of adding an `index.ts`. Neither is a failure merely for lacking the canonical tree.
- **Failure:** A new feature imports another feature's internal hook (even via `../../`), a shared primitive fetches business data, or a Client Component imports a barrel that exposes server-only code.
- **Non-target:** A React Native screen, a Clean-selected web project, a route-scoped admin app without selected FSD, or an isolated Query/Form API fix with no placement/import decision. Use the matching architecture or library skill instead.

## Sources and limits

- [FSD layers](https://feature-sliced.design/docs/reference/layers), [public API](https://feature-sliced.design/docs/reference/public-api), and [Next.js integration](https://feature-sliced.design/docs/guides/tech/with-nextjs) establish canonical layer rules, slice contracts, optional layers, and server/client API risks. The official Next example recommends a separate router/FSD structure; the route-local alternative here is **an adaptation**, not a claim that the example mandates it.
- Another project's FSD layout, counts, paths, exceptions, or approval status are not universal rules or evidence about the current target repository. The route-local placement and deep-import alternatives above are interpretations reconciled with the official references. Verify any claimed local convention from the live code/config and team contract before enforcing it.
