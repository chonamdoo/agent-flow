# React Native Route and Feature Architecture

Use when the affected React Native/Expo app's architecture mode is **stack** (this skill is then the selected architecture contract) or when its **local architecture contract** adopts this route-and-feature approach (this skill is then an adjunct; read the project's selected `architecture` skill first, and its boundaries take precedence where they differ), or when evaluating it as a candidate. In either mode, the app's existing boundaries and navigation library are the starting point. A project's use of Expo, React Native, `features/`, or this installed skill alone does not select the architecture. Clean-selected React Native and native Android projects use their own contracts. Do not migrate an existing app's routing, state libraries, or directory layout just to conform to this example.

## Assign one owner for each changed responsibility

1. Identify the route/screen, its consumers and navigation contract, shared UI, feature behavior, and persistent or remote data involved in the change. Keep route files responsible for route params, navigation, and composition under the adopted router; put reusable feature behavior beside the owning screen or feature using the project's existing layout. In Expo Router, `app/` or `src/app/` is a route tree, not a place to stash non-route utilities. For a new Expo app, Expo Router is a reasonable default.
2. Put one-screen UI and draft state close to that screen. Share behavior in a feature only when it has a real consumer or independent policy owner. Reusable visual primitives accept values/callbacks rather than owning a domain fetch or navigation side effect. Avoid obligatory `domain/data/presentation` copies for every feature, barrel exports for every directory, and unnamed global state; establish dependency direction from the selected project's actual code and contract.
3. Distinguish **component-local state**, **shared client state**, **remote server snapshots**, **form drafts**, and **durable device data**. Give each one owner as `react-native-development-guide` requires, and synchronize explicitly at boundaries. If the project uses TanStack Query, follow its React Native online/focus integration and existing query-key/invalidations; it is not a mandatory dependency. A custom hook shares logic, not automatically one shared state instance.
4. Trace background/active transitions, screen focus, unmount, permissions, and offline/reconnect effects through real RN and navigation lifecycles. Clean up subscriptions and listeners at the owner and verify that a late response cannot overwrite a newer screen or session. Do not assume Android ViewModel configuration-change lifetime, one process-wide context lifetime, or web `window` focus behavior in RN. Keep native SDKs/storage/networking at the project's existing platform/integration boundary, with errors translated where consumers actually handle them.
5. Extract pure business rules or narrow ports **when a concrete invariant, multi-source orchestration, offline synchronization, or cross-feature contract benefits from a separately testable boundary**. Locate them according to the governing contract (this skill in stack mode, or the selected local contract); adapters implement platform and persistence details. Reducers/MVI-like transitions can clarify a complicated state machine, but are optional; not every screen needs a ViewModel, UseCase class, Repository interface, or reducer. Do not conceal a meaningful boundary merely to minimize folders.

## Review the changed path

Trace the affected route through UI, state owner, data source, and lifecycle callback. State which rule or consumer justifies a new layer/port and which existing code owns the interaction. For code changes, exercise the actual screen on the relevant platform, including navigation away/back, background/foreground and offline/error paths when touched. Use `react-native-development-guide` for general mobile interaction and performance; native Kotlin/Swift code follows its platform guidance. No architecture usage ranking or mandatory layer count follows from this skill.

- **Success:** An Expo route composes a feature screen whose short-lived draft stays local, whose remote snapshot has one cache owner, and whose AppState listener is cleaned up at its owning boundary.
- **Valid alternative:** An existing React Navigation screen remains route-local; or an offline payment flow earns a separate pure policy and repository port because it coordinates multiple sources. A documented Clean-selected project continues using its Clean contract instead.
- **Failure:** A hook named `ViewModel` copies query results without ownership rules, two screens directly mutate one another's private state, or a listener survives screen disposal and applies an old session's update.
- **Non-target:** React Web FSD, native Android Clean, and an RN app that selected Clean Architecture rather than this route-and-feature contract.

## Evidence and limits

This is a conditional route-and-feature proposal, not a measured ranking of RN architectures. [Expo Router](https://docs.expo.dev/router/introduction/) and [Expo project structure](https://expo.dev/blog/expo-app-folder-structure-best-practices) support routes plus other app code; neither prescribes feature ownership. [React state location](https://react.dev/learn/sharing-state-between-components), [reducers](https://react.dev/learn/extracting-state-logic-into-a-reducer), and [custom hooks](https://react.dev/learn/reusing-logic-with-custom-hooks) support selective state placement.

[RN AppState](https://reactnative.dev/docs/appstate) and [TanStack Query RN integration](https://tanstack.com/query/latest/docs/framework/react/react-native) document mobile lifecycle and remote-cache integration. Even [Android's domain layer](https://developer.android.com/topic/architecture/domain-layer) makes use cases optional. Inspect installed versions and the target project's actual contract before claiming a specific integration or lifecycle behavior.
